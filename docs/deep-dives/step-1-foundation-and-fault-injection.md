# 第 1 步讲解：地基与故障注入框架

> 对应代码：`journal/`、`fault/`、`engine/`、`db/`
> 交付物：可运行的工程骨架 + 日志存储 + 故障注入器 + **复现缺陷的刻画测试**
> 面试定位：这一步是你讲整个项目的**入口**。面试官问「你这项目做什么的」，你从这里开始。

---

## 1. 一句话

> 我用一个描述性测试证明了：**当副作用已经发生、但结果还没来得及写进日志时进程崩溃，重启重跑会让副作用执行两次。**

这一句话就是整个项目的立项理由。后面所有的设计（日志、检查点、幂等、CAS）都是为了消灭这个窗口。

---

## 2. 故障场景（用业务语言说，先别用术语）

假设 Agent 帮用户退一笔 50 元：

1. Agent 调用了退款接口
2. **退款成功了**，钱已经打出去了
3. 就在这一刻，进程被 kill -9
4. 运维重启服务
5. Agent 从任务开头重跑 → **又退了一次**

用户收到 100 元。这就是 `AFTER_EXECUTE_BEFORE_JOURNAL` 这个窗口的后果。

同样的窗口在别的场景里是：**重复发短信给客户**、**重复创建了两台服务器**（重复计费）、**重复扣了库存**。

**为什么这个 bug 难？** 因为它不是「写错了代码」，而是「崩溃恰好发生在一个极窄的时间窗口里」。正常测试永远碰不到。所以**第一步不是修复它，而是先造一个能稳定复现它的工具** —— 这就是故障注入器。

---

## 3. 为什么这样设计

### 3.1 为什么先做日志，而不是先写 Agent Loop？

因为**日志是这个项目的地基，Agent Loop 只是测试夹具**。

这个项目的价值在「持久化执行语义」，不在「会调 LLM」。如果先写 Agent Loop，会花大量时间在 Prompt、工具注册、上下文管理上 —— 那些是**任何** Agent 项目都有的东西，面试官看腻了。而日志的写入时机和崩溃窗口，才是这个项目的独有难点。

> 被否决的替代方案：先做一个能跑通的 Agent demo，再补日志。
> 否决理由：那样做出来的东西和「LangChain4j + RAG + MCP」那套模板没有区别，正是调研里 90% 的同质化项目。

### 3.2 为什么日志表的主键是 `(workflow_id, step_no, type)`？

一个主键同时干两件事：

| 职责 | 说明 |
|---|---|
| **定位** | 唯一标识「第几个工作流的第几步的什么事件」 |
| **拦截** | 数据库唯一约束**拒绝**重复写入 —— 这是 exactly-once 的最终防线 |

如果只把它当定位用，就会写成「先 SELECT 查一下有没有，没有就 INSERT」。**这是竞态写法**：两个并发请求会同时通过检查，然后都插入。正确做法是**直接 INSERT，让数据库拒绝重复**。

> 面试官会追问：**「为什么不先查再写？」**
> 答：「先查再写是 TOCTOU 竞态。检查和写入之间有时间窗口，并发下两个线程会同时通过检查。必须依赖数据库的原子约束，而不是应用层的判断。我的 `append()` 里没有任何 SELECT。」

### 3.3 为什么 payload 用 JSON 类型，而不是 TEXT？

1. MySQL 会**校验它确实是合法 JSON**，写入脏数据会直接失败
2. 将来加新事件类型不需要改表结构
3. 存储层对内容完全无感知 —— `JournalStore` 不知道什么是「工具调用」

> 面试官可能追问：**「JSON 列不能直接建 B+ 树索引，你怎么查？」**
> 答：「日志的访问模式是按 `(workflow_id, step_no)` 顺序读，走的就是主键。我们不需要对 payload 内部字段做条件查询。如果将来真要按 payload 里的某个字段查，那是另一个需求，应该在建表时就把那个字段提出来做生成列，而不是滥用 JSON。」

### 3.4 为什么 `SimulatedCrash` 继承 `Error` 而不是 `Exception`？

因为业务代码里到处是 `catch (Exception e)`（重试、兜底、日志）。如果崩溃是 `Exception`，它会被这些 `catch` 吞掉，测试就失去意义了。

**真实崩溃（kill -9、OOM Killer）不会经过任何 catch 块。** 用 `Error` 才能逼近这个行为。这是一个刻意的设计，代码注释里也写了 —— 面试时能主动说出「这不是笔误」，是个加分点。

有一个测试专门验证这件事：`isNotCaughtByCatchException`。

### 3.5 为什么故障注入器要「触发一次后自动解除武装」？

因为要模拟**重启**。

如果不解除武装，重试时会再次在同一个位置崩溃，永远走不到恢复逻辑，测试就卡死了。「单次武装、单次触发」精确对应「进程死了 → 新进程启动 → 崩溃指针不再存在」这个现实。

> 面试官可能追问：**「应用内注入和真的 kill -9 有什么区别？」**
> 答：「应用内注入能确定性复现特定的崩溃窗口，快、可重复、能进 CI。但它有个盲区：它不能验证『进程被强杀时数据库连接会怎样』、『事务会不会被回滚』这类真实崩溃才会暴露的问题。所以我后续会补一个真的 fork 子进程然后 kill -9 的集成测试，两者互补。」（**注意：这个补充测试目前还没做，别把没做的说成做了**）

### 3.6 为什么执行器**故意不实现恢复逻辑**？

因为要先让测试**证明问题存在**。

TDD 的标准做法：先写一个测试把当前错误行为固化下来（characterization test），断言 `副作用次数 == 2`。看到这个红色的数字，再动手修。

好处：
1. 修复前后有**明确的对比数字**（2 → 1），这是简历上可以写的量化证据
2. 防止「以为修好了其实没有」
3. 面试时你可以说「我先复现了 bug 才修的」—— 这比「我一上来就设计对了」可信得多

> 代码里的 `DurableExecutor` 注释明确写着「没有恢复逻辑，这是刻意的」。不要让面试官觉得这是你写漏了。

## 4. 实测数据（真实输出，非编造）

### 4.1 故障注入器测试

```
[真实输出] Error 正确穿透了 catch(Exception): 注入崩溃于 BEFORE_STEP, step=0
[真实输出] 触发崩溃: 注入崩溃于 BEFORE_STEP, step=1
Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

### 4.2 缺陷复现测试（**真实实测输出**，2026-09-19）

```
[真实输出] 崩溃后副作用次数 = 1
[真实输出] 崩溃后日志行数 = 0
[真实输出] 重启后副作用总次数 = 2      ← 缺陷：应该是 1
[真实输出] 重启后日志行数 = 2
```

**怎么读这四行**：

| 行 | 含义 |
|---|---|
| 副作用次数 = 1 | 第一次执行时，退款确实发生了一次 |
| 日志行数 = 0 | 崩溃发生在写日志之前，**日志里什么都没留下** |
| 重启后总次数 = 2 | 重启重跑，**又退了一次** —— 这就是 bug |
| 重启后日志行数 = 2 | 第二次跑完才把日志补齐 |

**关键洞察**：问题不在于「日志写错了」，而在于**日志什么都没记下来，系统就无从知道那笔退款已经发生过了**。所以修复的方向不是「更小心地写日志」，而是「让副作用的执行本身可被追溯」—— 这是计划 2 的核心。

### 4.3 全部测试结果

```
Tests run: 13, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

（数据库连通性 1 + 故障注入器 4 + 日志存储 5 + 执行器崩溃 3）
