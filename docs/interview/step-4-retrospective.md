# 项目复盘

> 这份文档回答三个问题：**为什么这样设计**、**否决了哪些替代方案**、**哪些机制真的带来了提升**。
> 面试时，能讲清楚「我否决过什么、为什么」比罗列功能更有说服力。

---

## 1. 项目要做的事，一句话

> 当 LLM 是非确定性的、而工具调用有真实副作用时，**如何保证一次 Agent 任务崩溃后正确恢复，且副作用恰好执行一次。**

完成定义不是我自己编的，是论文 [arXiv:2608.03836](https://arxiv.org/abs/2608.03836) 的 **RESUME CONTRACT**：
PC / EO / FD / CV / CO / RD 六条性质 + FI 协议义务。

---

## 2. 为什么选这个题目（而不是"再做一个 Agent demo"）

调研阶段查到的关键事实：

1. **[Thoughtworks Technology Radar（2026-04）](https://www.thoughtworks.com/radar/techniques/ignoring-durability-in-agent-workflows)** 把
   「Ignoring durability in agent workflows」列为**反模式**，评级 Caution。原文：
   > "resulting in systems that **work in development but fail in production**"

2. **论文实测主流框架都没做对**：
   - **LangGraph 1.2.9**：SIGKILL 之后**重新执行已经持久化的工作** —— "exactly-once across interrupts, **at-least-once across crashes**, on one API"
   - **CrewAI 1.15.2**：与其文档宣称相反，会重复执行已经完成的方法
   - **并发恢复**：k 个进程恢复同一个挂起中断，会让被门控的操作执行 **k 次**（40 格中 36 格饱和）

3. **牛客的共识**：90% 的 AI 后端项目是「Spring AI + RAG + MCP」的同一个模板，
   **面后端岗挖不出亮点，面 Agent 岗扛不住拷打**。

**结论**：做「又一个 RAG 问答」是死路；而**持久化执行语义**是一个真实的、被行业承认的、且**主流实现都还有缺陷**的问题。

## 3. 否决过的替代方案（这部分最能体现判断力）

### 3.1 ❌ 否决：复用我的电商商城项目

**想法**：把 Agent 作为服务模块挂到已有商城上，复用真实订单/库存数据。

**否决理由**：
- 商城本身粗糙、有 bug。**Agent 出错时无法区分是 Agent 的 bug 还是商城的 bug**，排查成本翻倍
- 调研里确实有一条结论说「对后端岗，把 AI 模块附在已有项目上更好」——
  但那条建议的前提是**已有项目是可靠的**。我的前提不成立，所以**主动偏离了那条建议**
- 教训：**调研结论要看它的前提，不要照抄。**

### 3.2 ❌ 否决：用 Spring Boot

**理由**：
- 项目核心**没有一行 Web 或依赖注入代码**
- Spring Boot 已到 4.1.1，其 Java 17 基线不确定；本机只有 Java 17
- **引入框架会稀释「这是我自己实现的」这个看点** —— 而这个项目卖的就是实现

**结果**：纯 Java + JDBC + HikariCP + Jackson，7 个依赖。编译快、没有魔法。

### 3.3 ❌ 否决：用 Redis 做幂等

**理由**：唯一索引才是 exactly-once 的最终防线。Redis 只是快路径，**去掉它不损失正确性，只损失性能**；少一个依赖少一类 bug。

**代价**：并发性能不如 Redis 方案。这个取舍是自觉的。

### 3.4 ❌ 否决：精确计算断点、跳过已完成的步骤

**最初的设计**：恢复时算出断点，从断点继续，不重跑前缀。

**否决理由**：读了论文才发现它**明确允许重跑前缀**：
> "**Memoized replay conforms**: prefix code **may re-run** during recovery provided every prefix effect is served from the durable record."

**结果**：实现简单了一个量级 —— 每次恢复从头走一遍，副作用交给账本拦。
**代价**：多跑了一些无副作用的代码。这个代价可以接受。

> ⚠️ 这个改动让我踩了一个真实的坑：重跑前缀会往日志里**重复写** `STEP_RESULT`，撞主键抛异常。
> 修法不是「先查再写」（那是 TOCTOU），而是**直接写、捕获重复键**。

### 3.5 ❌ 否决：用 Testcontainers 做数据库测试

**理由**：本机没有 Docker。改为**项目专属的 MySQL 实例**（端口 3307）：
数据目录独立、密码已知、可随时删除重建，换机器也能用脚本复现。

### 3.6 ❌ 否决：第一版做「云资源运维」外壳 + Docker Compose 迷你集群

**最初的想法**：起 3-4 个服务 + 故障注入器，做故障应急 Agent。

**否决理由**：查了 GitHub 才发现 **AIOps 赛道已经饱和** —— 6280 个相关仓库，
而且有人做了 [自称「面试级全套项目」的包装项目](https://github.com/bcefghj/multi-agent-aiops)（360★，创建和最后 push 是同一天）。

**修正**：差异化改到**护栏层**，外壳缩小成「一张资源表 + 一个状态机」，一两天就能写完。
**教训**：**选题之前先查竞品密度**，别凭感觉判断"这个方向没人做"。

## 4. 哪些机制真的带来了提升（有数据）

| 机制 | 改进前 | 改进后 | 证据 |
|---|---|---|---|
| **效果账本 + 同事务** | 崩溃后副作用执行 **2 次** | **1 次** | `DurableExecutorCrashTest` |
| **CAS 抢占中断** | 并发 8 路会执行 k 次 | **1 次** | `ConcurrentResumeTest`（连跑 5 次稳定） |
| **先写后捕获重复键** | 恢复时日志写入冲突报错 | 日志无重复、旧值不被覆盖 | `PrefixContinuationTest` |
| **构造器内校验检查点** | 非法状态可被持久化 | **创建即拒绝**，0 行落库 | `CheckpointValidityTest` |
| **参数快照绑定** | 审批后参数可被偷改 | **拒绝执行**并报出两个指纹 | `ApprovalBindingTest` |

### 故障矩阵（9 格全部通过）

```
崩溃位置                          步骤   副作用  主机数  日志   结果
BEFORE_STEP                       0     2      2      3     PASS
BEFORE_STEP                       1     2      2      3     PASS
BEFORE_STEP                       2     2      2      3     PASS
AFTER_EXECUTE_BEFORE_JOURNAL      0     2      2      3     PASS
AFTER_EXECUTE_BEFORE_JOURNAL      1     2      2      3     PASS
AFTER_EXECUTE_BEFORE_JOURNAL      2     2      2      3     PASS
AFTER_JOURNAL                     0     2      2      3     PASS
AFTER_JOURNAL                     1     2      2      3     PASS
AFTER_JOURNAL                     2     2      2      3     PASS
```

**每一格都满足同一组不变量**：两台主机各被创建恰好一次、账本 2 条 DONE、日志 3 条（重跑不产生重复）。

> 论文用 39 格矩阵；我们是 9 格，规模小但方法论一致：**不靠举例证明正确性，把组合穷举掉**。

## 5. 诚实的能力边界（面试时必须主动说）

### 5.1 ⚠️ 外部副作用做不到 exactly-once

效果账本与副作用同事务成立的前提是**副作用发生在同一个数据库里**。

如果副作用在**外部系统**（支付网关、短信、云厂商 API）：
- **跨网络的原子提交不存在**
- 只能退化为 **at-least-once + 幂等键 + 对方幂等接收**

我核对过 Temporal 官方架构文档，它也是这个立场：
> "activity code **must either be idempotent or non-retryable** (i.e. **at least once or at most once**)."

**也就是说 Temporal 自己也不保证副作用 exactly-once。**

> 正确表述：exactly-once 不是能单方面保证的性质，它是「至少一次投递」+「接收方幂等」的组合结果。

### 5.2 其他已知不足

| 不足 | 影响 | 为什么不现在做 |
|---|---|---|
| 故障注入是**应用内**的，不是真 `kill -9` | 无法验证真实崩溃下连接/事务的行为 | 应用内注入能确定性复现特定窗口、可进 CI；真实 kill 应作为补充 |
| **没有跨主机实测** | 论文的失败是跨主机的 | 架构上成立（仲裁点在共享数据库），但没真跑两台机器 |
| 检查点是**全量快照** | O(N²) 存储增长（LangChain 实测 200 轮 5.3GB） | 六性质不要求它；这是性能优化，不是正确性。**砍掉是有意识的决定** |
| 审批**没有超时处理** | 中断可能永远挂着 | 论文提到 durable timers for SLAs |
| 没有真实 LLM 接入 | 测试用确定性假 LLM | 六性质全是确定性断言，用真模型永远测不出结论 |

## 6. 如果重做，会改什么

1. **先查竞品密度再选题**。我在 AIOps 上浪费了一轮设计，因为凭感觉判断"这方向没人做"。
2. **更早把论文的契约读全**。我第一版设计把 PC 理解错了（以为要跳过前缀），也漏掉了 CO 的两个子条款。
   精确定义一旦拿到，实现方向立刻清晰。
3. **测试先行确实有效**。计划 1 先用刻画测试把缺陷固化成「2 次」，计划 2 改成「1 次」——
   这个前后对比既是回归保护，也是简历上的量化数字。如果一开始就"设计对了"，反而没有这个证据。
4. **PowerShell 脚本要带 UTF-8 BOM**。我写完启停脚本后声称完成，实际连解析都过不了
   （PS 5.1 默认按 ANSI 读 `.ps1`）。**正好撞上调研里那份《AI 编程失败模式》的「测试全绿的谎言」。**

## 7. 方法论：这个项目怎么被验证的

| 原则 | 落地方式 |
|---|---|
| 不靠举例证明正确性 | 故障矩阵穷举崩溃位置 × 步骤 |
| 测试必须离线可跑 | 确定性假 LLM，不调真实模型 |
| 修复前先复现 | 计划 1 的刻画测试断言 `== 2`，计划 2 改为 `== 1` |
| 契约来自外部而非自创 | 六性质逐字取自论文原文，测试断言与之一致 |
| 诚实标注边界 | 本文件第 5 节；讲解文档每篇都有「不要声称做了」一节 |
| 不迁就实现改断言 | 并发测试首次失败时，**先确认是测试假设错了**（闸门不负责执行业务操作），而不是改数字让它通过 |

## 8. 面试时的一句话总结

> 我实现了 Agent 工作流持久化执行的 **RESUME CONTRACT 六条性质**，用论文实测主流框架失败的
> **并发恢复场景**做了对照：8 个并发审批抢一个挂起中断，主流框架会让被门控的操作执行 k 次，
> 我这里恰好 1 次。核心是**把「消费」做成一条数据库条件更新**，让判断和执行不可分割。
>
> 同时我也清楚它的边界：这套 exactly-once 只在副作用与账本同库时成立；
> 跨外部系统只能退化为 at-least-once + 幂等键 —— **Temporal 官方文档也是这个立场**。
